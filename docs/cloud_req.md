# AI Agent Web 平台需求文档
## 1. 文档目标
本文档用于定义一个 Web 站点的完整需求与实施边界。该站点面向最终用户提供类似 Claude Web 的 AI Agent 使用体验，通过浏览器控制 `claude code` 等 Agent CLI，并以可视化方式呈现会话、文件、执行过程、工具调用和结果。
本文档覆盖：
- 产品目标与范围
- 用户角色与权限模型
- 核心业务对象
- 功能需求
- 非功能需求
- 安全与隔离要求
- 系统架构建议
- 数据模型建议
- 外部依赖与兼容性要求
- 运维、审计、监控与实施计划
本文档目标不是绑定单一技术栈，而是形成一份可以直接进入系统设计、原型设计、任务拆分和 MVP 开发的基线需求。
## 2. 产品愿景
构建一个多租户的 AI Agent Web 平台，使用户能够：
- 在浏览器中创建和管理自己的 `project`
- 在隔离的工作目录中上传、下载、编辑和生成文件
- 选择并运行不同 AI Agent
- 为项目安装和启用 `plugin`、`skill`、`mcp/connector`
- 查看 Agent 执行过程、文件变更、资源使用情况
- 在预算与安全约束内稳定使用 Agent 能力
平台管理员能够：
- 配置 Agent 运行环境
- 管理 marketplace 源与默认能力
- 配置配额、预算、模型权限和安全策略
- 审计用户行为、任务执行和异常事件
## 3. 术语定义
- `Project`：用户的隔离工作目录，是 Agent 读写文件、安装技能和运行任务的基本单位。
- `Session`：用户与某个 Agent 的一次会话，包含消息、工具调用、执行日志和输出。
- `Plugin`：兼容 Claude CLI 插件机制的扩展能力，通过 `--plugin-dir` 等方式注入。
- `Skill`：项目级技能资源，通常以文件形式存在于 Project 内指定目录。
- `MCP/Connector`：通过 MCP 协议或等价连接器能力向 Agent 暴露外部工具、资源或服务。
- `Marketplace`：管理员配置的一个或多个能力源，可能来自 Git 仓库、本地目录、包索引或内部制品库。
- `Budget`：用户、组织或项目在一定周期内可使用的 token/费用上限。
## 4. 目标与非目标
### 4.1 产品目标
1. 支持 Web 端注册登录，创建、查看和运行 AI Agent 会话。
2. 提供以 `project` 为单位的轻量级文件系统隔离。
3. 支持项目文件上传、下载、浏览、预览、版本记录和 Agent 生成。可以关联一个 github 仓库
4. 提供严格的 token/费用预算控制，超额后不可继续使用。
5. 兼容 Claude CLI 的插件、技能、MCP/connector 能力注入。设计上尽量通用，以支持其他 Agent 例如 codex
6. 提供统一 marketplace，对 plugin、skill、mcp 进行整合管理，需要定期同步源。用户可选择安装到当前 project 或设为所有，即 future projects 默认安装。
7. 支持用户将能力安装到单个 project 或设为所有新 project 的默认能力。
8. 提供可追踪、可审计、可运维的控制面（一期低优先级，管理员手工登录机器看数据库内容都行）。
### 4.2 非目标
1. 首期不要求管理员通过 Web 页面管理 marketplace 源，可先通过终端或配置文件维护。
2. 首期不要求支持所有 Agent 协议，可先聚焦 Claude Code 和 crush（用户可自行提供 LLM Key）。
## 5. 功能需求
## 5.1 认证与账号
必须支持：
- 用户注册、登录、登出
后续支持：
- SSO 扩展能力
- 多因素认证预留
- 用户级 API Token 或访问令牌预留
## 5.2 文件管理
必须支持：
- 文件上传，例如上传一个 pdf 或者图片给 AI 分析
- 文件下载，下载分析的产物，预留对接其他存储，例如 google drive、onedrive 的能力
- 删除、重命名文件
- 文本文件预览
- 常见图片、PDF、Markdown 预览
- 显示文件大小、类型、更新时间
建议支持：
- 拖拽上传

约束：
- 所有文件路径必须限制在 project 根目录内
- 阻止路径穿越
- 阻止跟随危险符号链接
- 上传文件大小和总容量需可配置
## 5.3 Agent 任务执行
必须支持：
- 选择 Agent 类型与模型
- 并发任务控制
## 5.4 预算与用量控制
必须支持：
- 用户级预算
- 剩余额度查询
## 6. 非功能需求
### 6.1 安全性
必须满足：
- Project 级文件隔离
- 服务端权限校验
- 预算强校验
- 执行环境资源限制
### 6.2 可扩展性
支持后续扩展：
- 新增 Agent 类型
- 新增 marketplace source 类型
- 新增计费规则，从 token 消耗换算为金额
- 新增隔离后端，例如从轻量沙箱升级到容器或微虚拟机
## 7. 安全与隔离设计要求
这是该平台成败的关键部分。
### 7.1 最小可行隔离方案
MVP 阶段可采用“受控宿主机目录 + 进程级沙箱 + 资源限制”的轻量模型：
- 每个 project 拥有唯一物理目录
- Agent 进程工作目录固定为该 project 根目录
- 使用独立低权限系统用户或受限执行身份运行 Agent
- 限制可访问路径白名单
- 限制 CPU、内存、进程数、磁盘使用量、执行时长
- 默认禁用危险系统命令和高风险目录访问
生产环境为 Linux，需调研合适的隔离机制。
### 7.2 必须防御的风险
1. 路径穿越，访问其他 project 文件。
2. 符号链接逃逸。
3. 插件或 MCP 借机访问宿主敏感文件。
4. 通过命令执行修改宿主系统。
5. 恶意 fork 炸弹或资源耗尽。
6. 上传恶意脚本后被其他用户误执行。
7.  预算绕过，例如并发启动多个任务抢占剩余额度。
### 7.3 建议的防护措施
- 所有文件操作走统一服务层，不能由前端传入原始路径直接操作
- 对每次路径解析执行 `realpath` 校验，确保仍位于 project 根目录
- 禁止 project 内创建指向 project 外部的符号链接，或在访问时完全拒绝跟随
- 任务启动前对 budget 做原子预占
- 对运行中的 token 用量进行流式累计，结束后结算差额
### 7.4 网络安全策略
考虑外网访问如何限制，比如让 AI 下载超大文件
## 8 重要功能说明！！！！
由于 golang 会完全变成独立的服务端，客户通过 web 从远程访问，因此 golang 自身需要做好多租户的处理。
因此现有 config.json 配置需要调整，只能保存全局性功能控制，而不能保存某个用户特定的配置。
需要将用户数据都放在存储中，各自独立控制，例如用户创建的项目列表等。需要仔细区分配置中哪些需要迁移。
功能上，將现有的 cloud 按钮、task、asset、workflow、terminal 进行隐藏，也不要让用户能从前端代码里发现有对应的后端url，避免他看前端源代码然后发现对应的后端、进行直接调用。
但这些功能本身要删除，这里的隐藏通过配置文件中的一个白名单控制，对于特定用户才会显示出来。
