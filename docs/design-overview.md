# BoxNex：AI 驱动的一站式研发平台 — 概要设计

> 版本：0.3
>
> 日期：2026-02-23

---

## 1. 背景与动机

### 1.1 行业趋势

AI 正在根本性地重塑软件研发范式：

- **自然语言成为第一编程语言**：Prompt 正在取代语法细节，开发者更多在定义"做什么（What）"而非"怎么做（How）"。
- **调试成本转移**：传统的 80% 写代码 / 20% 调试正在反转 — 现在约 20% 时间生成代码，80% 时间用于 Prompt 调优和结果验证。
- **IDE 进化**：以文本编辑为中心的传统 IDE 正让位于以意图理解为中心的"AI 协作空间"。

| 维度     | 传统 IDE                    | 未来 IDE                                         |
| -------- | --------------------------- | ------------------------------------------------ |
| 核心定位 | 编辑器（以文本编辑为中心）  | 推理引擎（以理解意图为中心）                     |
| 交互方式 | 键盘输入、插件扩展          | 自然语言对话、视觉拖拽、逻辑编排                 |
| 上下文   | 当前打开的文件              | 全局仓库、Git 历史、生产日志、业务需求文档       |
| 角色     | 工具                        | 数字队友 / 结对编程者                            |

Cursor 不会是终点 — 它只是把 AI 嵌入了 VS Code 框架。未来的"IDE"可能根本不像编辑器，而是一个实时协同的画布，或者一个云端的自动化控制台。代码将逐步"透明化"，开发者更多看到的是逻辑拓扑图，代码作为底层"汇编语言"只在深度优化或极端调试时才需要打开。

业界参考：Daytona（云端开发环境）、Claude Code Web（AI 驱动的云端编程）。

### 1.2 项目动机

当前 AI 辅助研发流程存在以下痛点：

1. **工具链碎片化**：需求在 Jira，设计在飞书文档，编码在本地 IDE（Cursor/VSCode），Review 在 GitLab，变更单在发布系统 — 信息分散在各个工具中。
2. **开发过程黑盒化**：开发者的工作过程对队友和 leader 不透明，设计决策、代码推理、AI 交互过程均不可见。
3. **协作成为瓶颈**：当 AI 接管了更多代码生成工作后，**协作和结果 Review** 取代编码本身成为最大的效率瓶颈。
4. **供应商锁定风险**：如果全公司绑定在单一 AI 工具（如 Cursor）上，战略风险很高。
5. **资产缺乏统一管理**：设计文档、AI 生成物、Review 评论、决策记录没有集中管理，也没有相互关联。
6. **变更单手工填写**：当前变更单（设计文档、测试报告、操作手册、验证方案、影响范围、回滚方案等）全靠人手工填写，效率低且容易遗漏。

## 2. 目标与价值

### 2.1 目标

构建一个**基于 Web 的、AI 驱动的一站式研发平台**（代号：BoxNex）：

1. 通过 AI 串联研发全流程 — 从需求到设计、编码、测试、Review、变更管理。
2. 提供统一透明的协作空间，所有研发资产可见可共享。
3. 支持 **Web、本地、飞书** 多端统一的研发能力。
4. 通过 Agent 抽象层避免供应商锁定。
5. 覆盖范围：**需求分析、设计文档生成、代码开发、单元测试、测试用例生成、变更单编写**。
6. 不覆盖：线上发布和部署过程。

### 2.2 非目标

- **不是流程引擎**：平台不强制固定流程。各团队自行组织研发流程，平台只提供原子能力和上下文串联。
- **不替代本地 IDE**：高性能、精细化编码仍在本地完成，通过 Git 分支对接。
- **不是 CI/CD 平台**：聚焦发布前的研发过程。

### 2.3 价值主张

| 角色   | 价值                                                                            |
| ------ | ------------------------------------------------------------------------------- |
| 开发者 | 一站式 AI 辅助研发，无需切换工具，对话式开发                                    |
| 审查者 | 对文档和代码进行行内评论，AI 推理过程透明可追溯                                 |
| Leader | 全程可见迭代进展和设计决策，变更单自动生成免去手工填写                           |
| 组织   | 降低供应商锁定风险，统一最佳实践（Skills），资产可复用                           |

## 3. 核心理念

### 3.1 No Workflow — 原子能力 + 上下文串联

这是最关键的设计原则。平台不为全公司定义统一的研发流程：

- **提供原子能力**：设计文档生成、代码生成、测试生成、MR 创建、变更单填写 — 每个都是独立能力。
- **通过上下文串联**：各能力之间松散耦合，仅通过共享的**资产**（文档、代码、决策）关联。例如 AI 在生成代码时可以引用设计文档，但不要求设计文档必须先存在。
- **每步人工确认**：每一步 AI 产出（设计文档、代码、测试用例）都需要人工 Review 确认后才作为正式资产。

### 3.2 设计依据

公司各团队研发模式各不相同，强制指定统一的研发流程对推广及应用不利。即使统一团队内部，也不一定每个需求的迭代都要遵循一样的研发流程。例如一个小 bug 修复并不需要任务分解这样一个步骤，一个性能优化也并不需要 API 设计过程，因此应该提炼原子能力，打通上下文，而非定死流程。

开发灵活性优先。如果未来个别团队需要流程管控（如"必须有设计文档才能提交变更单"），可在项目级别配置约束条件，作为护栏而非流程编排。

## 4. 核心概念

### 4.1 概念模型

```
项目 (Project)
  ├── 关联本地 Git 仓库路径
  ├── 关联 GitLab 远端仓库
  ├── 项目级配置（OKOne 变更单配置等）
  │
  ├── 任务 (Task)  ── 可选关联 Jira 工单
  │     ├── 子任务（最多 1 级）
  │     ├── 关联资产（多对多）
  │     └── 评论、标签、emoji 反应
  │
  ├── 资产 (Asset)  ── 归属于项目
  │     ├── 需求文档、设计文档、代码变更、单元测试、测试用例
  │     ├── 版本历史
  │     └── 行内 Review 评论
  │
  └── 会话 (Session)  ── AI 对话上下文
        ├── 关联 AI Agent 后端（claude / codex / cursor）
        └── 对话消息历史

变更单对接 (OKOne 插件)
  ├── 配置存储在 Project.Extra 中
  └── 调用 OKOne API 创建变更单
```

### 4.2 概念详述

#### 项目（Project）

迭代之上的组织单元。一个项目对应一个业务域或系统：

- 关联一个或多个 Git 仓库（微服务架构下常见多仓库）。
- 承载项目级配置：适用的 Skills、编码规范、未来可扩展的约束条件。
- 是团队协作的基本单位 — 项目内的迭代和资产对项目成员可见。
- 初期不强制任何流程约束，预留能力供未来各团队按需自行配置。

#### 任务（Task）

平台上的核心工作单元，对应一个研发任务或需求：

- 任务可选关联 Jira 工单，但不强制要求。
- 支持**父子层级**（最多 1 级子任务），便于拆解较大需求。
- 任务可以关联多个资产（多对多），资产本身归属于项目。
- 任务支持标签、评论、emoji 反应，便于协作标注和状态沟通。
- 生命周期：open → closed。
- 优先级：low / medium / high。

#### 资产（Asset）

项目中产生的各类有类型、有版本的制品，归属于项目，可关联到具体任务：

| 资产类型         | 说明                                           |
| ---------------- | ---------------------------------------------- |
| requirement_doc  | 需求文档，从 Jira 导入或 AI 生成的需求摘要      |
| design_doc       | 设计文档，API 设计、架构决策、方案说明等         |
| code_change      | 代码变更，关联到 Git 分支/提交                  |
| unit_test        | 单元测试，AI 生成或手写的单测代码               |
| test_case        | 测试用例，面向 QA 的测试用例描述                |

资产的关键属性：

- **归属项目，不绑定单一任务**：资产保存在平台数据库（SQLite / 云端存储），通过 task_asset_links 可与任意任务关联。
- **有版本**：每次保存创建新版本，支持版本对比（diff）。每个版本保存完整内容快照，存储在 asset_versions 表中。
- **状态流转**：draft → reviewing → approved。
- **可 Review**：所有资产支持行内评论（类似 GitLab MR 的行级评论），评论绑定到具体版本号和行号。
- AI 在创建/更新资产时通过 MCP 工具调用完成，可在对话上下文中直接引用资产内容。

#### Review

一等公民概念。每步 AI 产出都经过人工 Review：

- 对文档和代码进行行内评论（类似 GitLab MR 的行级评论体验）。
- 状态跟踪：待审查 / 已通过 / 需修改。
- AI 可以感知 Review 评论并据此修改（如"根据审查者的反馈修改设计文档"）。
- 代码 Review 可与 GitLab MR 的评论双向同步。

#### 会话（Session）

会话是 AI 对话的持久化单元，归属于项目，独立于任务：

- 一个项目下可以有多个会话，支持手动排序。
- 每个会话选择一种 Agent 后端：**claude**（Claude Code CLI）、**codex**（OpenAI Codex CLI）、**cursor**（Cursor AI）。
- 会话状态（agent_session_id）持久化到数据库，支持跨页面刷新恢复对话上下文。
- 平台持久化完整的消息历史（用户消息和 AI 响应，含工具调用记录）。
- 通过 WebSocket 实时传输 AI 响应流。

AI 在会话中可以访问：

- 项目关联的 Git 仓库内容（代码、历史）
- 项目中的资产和任务（通过 MCP 工具）
- GitLab MR 评论（通过 MCP 工具）
- 终端执行能力（通过 MCP 工具）

#### Skills（规划中）

增强 AI 行为的可复用知识包（类似 Claude Code 的 CLAUDE.md / Skills 概念）：

- **平台级 Skills**：组织级最佳实践、编码规范、架构模式。
- **项目级 Skills**：特定项目的架构知识、领域约定。
- **用户级 Skills**：个人偏好和习惯。
- Skills 以 Markdown 格式定义，注入 AI Agent 的上下文中。
- 支持组织内共享和发现。

> 当前状态：Skills 管理界面及平台内的 Skills 存储尚未实现。用户可通过 Claude Code 本身的 CLAUDE.md / Skills 机制在 Git 仓库中维护项目级知识，由 Agent 在执行时自动读取。

#### 变更单（OKOne 集成）

对接内部发布系统（OKOne）的变更单创建能力，以插件形式挂载：

- 变更单配置（应用 ID、服务 ID、环境 ID 等）存储在 Project.Extra 中，按项目维度配置。
- AI 根据项目资产（设计文档、代码变更等）填充变更单各字段，通过 OKOne API 提交。
- 变更单创建后由 Leader 在 OKOne 系统中完成审批，发布过程不在 BoxNex 范围内。

变更单主要自动填充字段：

| 字段             | 来源说明                                                        |
| ---------------- | --------------------------------------------------------------- |
| 应用 / 服务 / 环境 | 项目配置（OKOne 集成参数）                                    |
| 描述             | 关联任务的需求摘要，由 AI 汇总                                  |
| 设计文档         | 关联项目中的设计文档资产                                        |
| 操作手册         | AI 根据代码变更和设计文档生成                                   |
| 验证方案         | AI 根据变更内容生成                                             |
| 风险及影响范围   | AI 分析代码变更涉及的服务、API 等                               |
| 回滚方案         | AI 根据变更类型生成                                             |

> 注：平台内的 **change** 数据表（`changes`）是操作审计日志，记录所有实体的创建/更新/删除事件，用于云模式下的变更同步，与变更单是不同的概念。

### 4.3 关于是否还需要其他概念

以上六个核心概念（项目、任务、资产、Review、会话、变更单对接）已能覆盖主要场景。目前认为不需要额外引入新概念，理由：

- **不需要"团队"概念**：通过项目的成员关系即可实现权限和可见性控制。
- **不需要"发布"概念**：OKOne 变更单插件已承担对接发布系统的职责。
- **不需要"阶段"概念**：这与"No Workflow"理念冲突；松散耦合通过资产实现，不需要显式的阶段定义。

如果未来需求变化，项目概念足以承载扩展（如项目级约束、项目级仪表盘等）。

### 5.2 各组件说明

#### 5.2.1 接入层

**Web 应用**

主要交互界面（React + TypeScript + Vite），提供完整的研发体验：

- 项目和任务的管理仪表盘
- AI 对话界面（主工作界面，多会话管理，类似 Claude Code Web 的交互体验）
- 文档编辑器（Monaco Editor），支持行内 Review 评论
- 集成式终端（xterm.js，通过 WebSocket 连接后端 PTY）
- 资产版本历史与 diff 展示
- Git 操作界面（diff 查看、提交、MR 创建）

前端设计参考：[1code](https://github.com/21st-dev/1code) 的界面设计风格。

**飞书消息处理**

飞书内的轻量研发入口（云模式下通过消息轮询实现）：

- 解析飞书消息中的项目 ID 前缀（`[hex8] 消息内容`），路由到对应项目的 AI 会话
- 查找或创建 session，驱动 AI Agent 执行任务，最终回复处理结果
- 支持 `list` / `projects` 命令查看项目列表
- 适用于轻量问答和任务触发；复杂操作（代码 Review 等）仍在 Web 端完成

**本地 CLI（规划中）**

面向偏好终端工作流的开发者：

- 与 Web 版相同的 AI Agent 能力
- 与平台同步任务上下文和资产
- Golang 单二进制文件，任何平台无依赖运行

#### 5.2.2 核心服务

**项目 / 任务管理服务**

管理项目、任务的完整生命周期：

- 项目 CRUD，关联本地 Git 仓库路径和 GitLab 远端 URL
- 任务 CRUD，支持父子层级（最多 1 级子任务）
- 任务标签、评论、emoji 反应
- 任务与资产的多对多关联管理

**AI Agent 引擎**

平台的核心 — 编排 AI Agent 交互：

- 统一 `Agent` 接口抽象，支持多种后端：**Claude Code CLI**、OpenAI Codex CLI、Cursor AI
- 通过 stdin/stdout 与 CLI 进程通信，解析流式事件（text_delta、tool_call、tool_result、thinking 等）
- 通过 **MCP（Model Context Protocol）** 服务向 Agent 注入平台工具能力（资产读写、任务查询、终端执行等）
- 统一的 StreamEvent 模型，屏蔽不同 Agent 后端的差异
- Session 状态持久化：agent_session_id 存数据库，支持跨请求恢复会话
- 实时流式传输 Agent 响应到客户端（WebSocket）

**资产管理服务**

管理所有类型化的制品：

- 各资产类型的增删改查
- 版本历史跟踪（基于 MySQL，独立于 Git）
- 跨迭代的资产引用
- 资产搜索和发现

**Review 与协作服务**

提供人工确认层：

- 对文档和代码进行行内评论（GitLab MR 风格的行级评论）
- Review 工作流：发起审查 → 评论 → 通过 / 打回
- 通知路由（Web 推送、飞书通知）
- Review 历史和审计追踪

**沙箱运行环境（规划中）**

服务端 AI Agent 执行隔离（当前尚未实现，AI 直接在项目配置的本地 Git 仓库路径下执行）：

- 目标：每个用户的 AI Agent 会话运行在独立沙箱中
- 提供预配置的工作空间（已 clone 相关仓库并 checkout 到任务分支）
- 支持 Git worktree，一个仓库可以同时有多个工作树，不同任务的开发互不干扰
- 默认临时化：沙箱状态在会话结束后可丢弃，持久化变更已提交到 Git

**文档版本管理**

- Markdown 格式存储，带结构化元数据

**代码编辑与终端**

## 6. 关键技术要点

### 6.1 Agent 统一接口 + MCP 工具层（Golang）

**多 Agent 抽象** 是避免供应商锁定的核心设计：

- 定义统一的 `Agent` 接口，当前实现三种后端：Claude Code CLI、OpenAI Codex CLI、Cursor AI
- 每种 Agent 后端通过 subprocess + stdin/stdout 与 CLI 进程通信，解析不同格式的流式事件
- 统一的 `StreamEvent` 模型（text_delta、tool_start、tool_result、thinking、error、done）屏蔽各后端差异
- **MCP（Model Context Protocol）** 服务运行在内置端口，向 AI Agent 暴露平台工具能力：
  - 资产读写（save_asset、get_asset_content、list_assets）
  - 任务查询（get_task、list_tasks、create_task）
  - 资产评论（list_asset_comments）
  - GitLab MR 评论（get_gitlab_mr_comments）
  - 终端命令执行（run_in_terminal）
  - 交互式问卷（ask_question）
- 需要处理：流式响应、工具调用事件解析、Session 状态持久化与恢复、上下文注入

### 6.2 为什么选择 Golang

Golang 的选择基于可移植性和部署简易性：

- **单二进制部署**：无运行时依赖，在开发机、服务器、容器中均可运行
- **本地-云端对称**：同一个二进制既可以作为云服务运行，也可以在本地作为 CLI 使用，实现"Claude Code Web"在两种模式下的效果
- **并发模型**：Goroutine 非常适合管理多个并发的 Agent 会话和流式响应
- **交叉编译**：轻松构建 Linux（服务器）、macOS（开发机）等目标平台

### 6.3 为什么选择 Web 而非 IDE 插件

选择 Web 作为主要交互界面而非开发 IDE 插件：

- **交互自由度高**：不用强行在 IDE 里做界面，Web 端的交互设计空间更大、体验更好
- **不绑定 IDE**：不依赖 VS Code、JetBrains 或任何特定 IDE
- **随时可用**：甚至可以在飞书聊天中以对话形式开展研发工作
- **IDE 能力保留**：需要时仍可嵌入 Web 版 VSCode 提供直接编辑能力

### 6.4 沙箱架构（规划中）

服务端 Agent 执行需要隔离保障（当前 AI 直接在项目配置的本地 Git 仓库路径下执行，沙箱尚未实现）：

- **目标**：每个 Agent 会话运行在轻量容器中（Docker / gVisor / Firecracker micro-VM）
- **预配置工作空间**：容器启动时已 clone 相关仓库并 checkout 到任务分支
- **Git worktree 支持**：类似 1code 的方式，同一仓库可创建多个工作树（worktree），不同任务的开发互不干扰，避免分支切换冲突
- **临时化为主**：沙箱状态在会话结束后可丢弃，有意义的变更已通过 Git commit/push 持久化
- **安全策略**：网络出口控制（Agent 只能访问白名单地址）、文件系统边界、CPU/内存/时间限制

### 6.5 上下文管理 — 平台的核心价值

平台的核心价值在于成为"上下文中枢"，让 AI Agent 比独立使用时显著更有效：

- **任务上下文**：任务描述、优先级、关联的子任务和资产（通过 MCP 工具按需获取）
- **资产上下文**：已有的设计文档、Review 评论、决策记录（通过 MCP 工具）
- **代码上下文**：项目关联的本地 Git 仓库，Agent 可直接读写文件、查看 Git 历史
- **GitLab 上下文**：MR 评论可通过 MCP 工具拉取，供 AI 感知和响应审查意见
- **终端上下文**：Agent 可通过 MCP run_in_terminal 工具在活跃终端执行命令
- 平台通过注入 MCP 工具集，让 AI Agent 在对话中按需获取所需上下文，无需用户手动准备和粘贴

### 6.6 文档管理（基于 SQLite / 云端存储）

文档作为平台一等资源，不存储在 Git 仓库中：

- **存储方案**：本地模式使用 SQLite，云模式使用远端 HTTP Store（命名空间隔离）；每个版本保存完整 Markdown 内容快照（asset_versions 表）
- **版本管理**：每次保存自动创建新版本，支持任意两个版本之间的 diff 对比
- **设计原因**：文档是跨项目/跨仓库横切的，不属于任何单一 Git 仓库
- **行内评论**：评论数据存储在 review_comments 表中，关联到资产 ID、版本号和具体行号
- **渲染**：Web UI 中 Markdown 富文本渲染，支持实时预览

### 6.7 Git 集成

当前实现以单仓库为主，通过项目配置关联本地 Git 路径：

- 每个项目配置一个本地 Git 仓库路径（git_repo_path）和 GitLab 远端 URL（gitlab_repo_url）
- 支持 Git 操作：status、diff、commit、push、log，在 Web 端可视化
- 支持创建 GitLab MR，自动从项目设计文档生成 MR 描述
- 通过 MCP 工具可读取 GitLab MR 评论，供 AI 在对话中感知和处理
- 多仓库协调（跨仓库变更追踪、沙箱多 clone）在沙箱规划中一并处理

### 6.8 多端统一架构（Web / 本地 / 飞书）

三种接入方式共享同一后端 API：

- **统一 API 层**：一套 REST + WebSocket API（Go Chi Router）服务所有客户端
- **Web**：全功能 SPA（React + TypeScript），主要界面
- **本地 CLI**（规划中）：Golang 二进制调用同一套 API；也可本地运行 Agent 引擎处理离线场景
- **飞书消息**：云模式下轮询消息变更，将飞书消息路由到对应项目的 AI 会话，返回处理结果
- **一致性**：同一个任务、同一份资产、同一个 AI 上下文 — 不论用户从哪个端接入

### 6.9 松散耦合的实现方式

"No Workflow"理念需要具体的技术实现：

- **引用而非依赖**：代码生成可以引用设计文档，但不要求其必须存在
- **上下文注入而非流程编排**：AI Agent 被给予当前可用的所有资产作为上下文，由用户决定下一步做什么
- **可追溯但不强制**：资产之间可以建立链接（如"这段代码基于该设计文档生成"），链接是信息性的，不是强制的
- **事件驱动的建议**（可选）：当资产创建或更新时，平台可发布事件，触发建议（如"设计文档已通过审查 → 建议开始编码"），但建议不是强制动作

### 6.10 Review 作为一等能力

人工确认在每一步都至关重要：

- **统一 Review 模型**：相同的 Review 体验（行内评论、通过/打回）适用于所有资产类型 — 文档、代码、测试用例、变更单
- **AI 感知 Review**：AI Agent 可以看到 Review 评论并据此行动（如"根据审查者在设计文档第 15 行的评论修改方案"）
- **GitLab MR 集成**：代码 Review 可以使用平台自己的 Review UI，也可以与 GitLab MR 的评论双向同步

### 6.11 变更单自动生成（OKOne）

变更单自动生成是平台对效率提升最直接可感知的价值之一：

- AI 从项目资产（设计文档、任务描述等）中提取信息，自动填充 OKOne 变更单各字段
- 设计文档、测试报告等直接引用资产内容，无需手工复制
- 操作手册、验证方案、回滚方案由 AI 根据代码变更和设计文档内容生成
- 风险及影响范围由 AI 分析代码变更涉及的服务、API、数据库等自动推断
- 生成结果仍需人工 Review 确认后再提交到 OKOne 发布系统

## 7. 典型使用场景（示意性，非强制性）

> 以下描绘几种可能的使用方式，平台不强制任何特定顺序或步骤。

### 场景一：标准需求开发

1. **创建任务**：在 Web 上创建任务，填写需求描述（可关联 Jira 工单 ID）。
2. **AI 辅助设计**：在 AI 会话中对话："根据任务描述和现有代码库，生成一份设计文档，覆盖 API 变更和数据库 Schema 调整。" AI 通过 MCP save_asset 工具生成设计文档资产。
3. **设计 Review**：将设计文档分享给审查者，审查者添加行内评论。用户让 AI 根据 Review 评论（通过 MCP list_asset_comments 获取）修改。
4. **AI 辅助编码**：告诉 AI："按照已通过的设计文档实现代码。" AI 在本地 Git 仓库中直接读写文件。
5. **代码 Review**：通过平台创建 GitLab MR。AI 可读取 MR 评论并据此修改代码。
6. **测试生成**：让 AI 根据设计文档和代码变更生成单元测试和 QA 测试用例资产。
7. **变更单**：通过 OKOne 插件触发变更单生成，平台自动填充设计文档内容、影响分析等。Leader 在 OKOne 系统审批。

### 场景二：简单 Bug 修复

1. **创建任务**：填写 Bug 描述（可关联 Jira Bug 工单）。
2. **AI 直接编码**："根据 Bug 描述，分析原因并修复。" — 跳过设计文档步骤。
3. **代码 Review + 变更单**：MR Review 通过后生成 OKOne 变更单。

### 场景三：飞书快速交互

1. 在飞书中发送消息（格式：`[项目ID前8位] 帮我看一下任务描述，分析一下技术方案`）。
2. BoxNex 云端收到消息，路由到对应项目会话，AI 处理后回复结果。
3. 复杂操作（如代码 Review、多轮对话）转到 Web 端完成。

### 场景四：本地精细化开发

1. Web 上创建任务和 AI 会话，AI 生成基础代码框架。
2. 开发者在本地 IDE 进行高性能、精细化编码，Push 到项目分支。
3. 回到 Web 平台，让 AI 补充单测、生成变更单。
